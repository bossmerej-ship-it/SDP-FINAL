# Как объяснить проект

## Что делает приложение

Клиент выбирает блюдо и добавки. Приложение собирает заказ, применяет выбранную
скидку и сохраняет результат. Кухня получает новый заказ. Когда кухня меняет
статус, клиент получает уведомление.

Начните с Demo.java. Это последовательность действий пользователя.
Затем откройте RestaurantFacade.placeOrder() и проследите три шага:
buildOrder(request), calculate(order), orders.submit(order, price).

## Timur Naumov — Factory Method и Decorator

### Factory Method

Meal — общий интерфейс блюда. Burger и Pizza — конкретные продукты.
MealCreator объявляет createMeal(). BurgerCreator и PizzaCreator переопределяют
этот метод и выбирают конкретный продукт.

В RestaurantFacade хранится таблица код → MealCreator. После выбора фабрики
вызов creator.createMeal() возвращает Meal. Клиентский код работает с интерфейсом.
Для нового блюда создайте его класс и Creator, затем зарегистрируйте Creator.
Общий алгоритм оформления заказа продолжит работать.

В лекции 2 роли называются Product, Concrete Product, Creator, Concrete Creator.
В этом проекте они явно представлены отдельными типами.

### Decorator

Cheese и Sauce имеют тот же интерфейс Meal, что и Burger.
MealDecorator хранит ссылку на оборачиваемое блюдо.
Cheese.getPrice() вызывает meal.getPrice() и прибавляет 300.
Sauce делает то же самое и прибавляет 200.

new Sauce(new Cheese(new Burger())) даёт 2500 + 300 + 200 = 3000 KZT.
Цепочка getDescription() даёт "Burger + cheese + sauce".
Декоратор можно обернуть ещё одним декоратором.

## Madi Talgat — Builder и Strategy

### Builder

Order.Builder накапливает данные через addItem(), serviceType(),
tableNumber(), comment(). Каждый метод возвращает this, что позволяет
соединять вызовы. build() проверяет заказ и создаёт Order.

В Order закрытый конструктор. Список позиций копируется через List.copyOf,
поэтому добавление позиции в Builder после build() не изменит уже созданный заказ.
Builder используется для всего заказа, а Decorator — для добавок к одному блюду.

### Strategy

DiscountStrategy объявляет discountFor(subtotal). RegularPrice возвращает нулевую
скидку, PercentageDiscount рассчитывает заданный процент. PriceCalculator —
Context. Он считает сумму позиций и вызывает выбранный алгоритм скидки через
интерфейс.

RestaurantFacade выбирает стратегию по входному значению regular/student.
Каждый запрос получает собственный PriceCalculator, поэтому выбор скидки
одного клиента не меняет расчёт другого.

Для 3000 KZT и скидки 10% discount = 300, total = 2700.
BigDecimal хранит десятичные суммы точно. HALF_UP задаёт правило округления.

## Merey Kuatbay — Facade и Observer

### Facade

RestaurantFacade предоставляет getMenu(), quote(), placeOrder(), getOrder(),
listOrders(), updateStatus(), subscribe(), unsubscribe().

placeOrder() координирует несколько частей: фабрики, декораторы, Builder,
PriceCalculator и OrderService. Фасад передаёт работу соответствующим классам.
Проверка полей заказа находится в Builder, расчёт в стратегии, статусы в сервисе.

### Observer

OrderService — Subject. Он хранит набор OrderObserver. subscribe() добавляет
подписчика, unsubscribe() удаляет. После сохранения нового заказа или изменения
статуса сервис вызывает onOrderChanged() у подписчиков.

KitchenObserver реагирует на NEW. CustomerObserver сохраняет сообщения для
заданного клиента. Демонстрация выводит накопленные сообщения.
При появлении нового типа подписчика сервис можно использовать без изменения
его алгоритма уведомления.

Повтор PREPARING → PREPARING не порождает повторного события.
Сбой одного подписчика записывается в журнал, остальные продолжают работать.
Обработка синхронная. Для сетевых уведомлений позже понадобится очередь
или отдельная доставка с повторными попытками.

## SOLID на конкретных классах

- SRP. PriceCalculator считает цену, OrderService хранит заказы,
  Demo выводит результат.
- OCP. Новая стратегия реализует DiscountStrategy, новый подписчик —
  OrderObserver. Для выбора нового типа по строковому коду меняется регистрация
  в фасаде, а алгоритмы расчёта и уведомления сохраняются.
- LSP. Burger, Pizza, Cheese и Sauce используются через один интерфейс Meal.
- ISP. Meal содержит только описание и цену. OrderObserver содержит один callback.
- DIP. PriceCalculator зависит от DiscountStrategy, сервис зависит от OrderObserver.

## Частые вопросы

**Почему нужны Builder и Factory Method одновременно?**
Factory Method создаёт отдельное блюдо. Builder собирает заказ с набором
позиций и дополнительными параметрами.

**Почему фасад содержит switch?**
Он выбирает конкретную реализацию по внешнему коду. Работа самих алгоритмов
находится в классах паттернов. Выбор реализации — задача сборки приложения.

**Где здесь Observer, если сообщения выводятся в конце?**
События доставляются при submit/updateStatus. Подписчики сразу сохраняют
сообщения. Demo позже читает их для отображения.

**Где будет React?**
В отдельном frontend-проекте. HTTP-контроллер Java преобразует JSON в
OrderRequest и вызывает существующий фасад. Подробнее в WEB_INTEGRATION.md.

**Что ещё нужно перед сдачей?**
Команде нужно освоить и самостоятельно доработать свои части, указать группу
и фактический вклад, сверить итоговый отчёт с кодом и защитить реализацию.
